
## Resume an affected v1.1.0 run

A run showing millions of rows in `massive_reference / all-tickers` is affected by the pagination-loop defect fixed in v1.1.1.

1. Suspend the worker and wait until the old instance has stopped.
2. Deploy v1.1.1. No database migration is required.
3. In Supabase, requeue only the running `massive_reference` partition while preserving its cursor.
4. Resume/deploy the worker. The partition continues from its saved Massive page.
5. Do not cancel or recreate the research run. Completed daily-bar partitions remain valid.

The frozen protocol hash is unchanged from v1.1.0.

# Deployment — v1.1.1 quarterly build

## New deployment

1. Create a separate Supabase project.
2. Create a private GitHub repository.
3. Upload the contents of this ZIP to the repository root.
4. In Render, create a Blueprint from that repository.
5. Confirm it creates only:
   - `alpaca-138-research-web`
   - `alpaca-138-research-worker`
6. Enter the new Supabase values and provider credentials.
7. Deploy the web service first so migrations 001 and 002 are applied.
8. Confirm `/health` reports version `1.1.1` and database `ok`.
9. Deploy the worker.
10. Run a new smoke test.
11. Start the full quarterly study only after the smoke report completes.

## Upgrade from v1.0.0

1. Safely cancel an active v1.0 run.
2. Replace the GitHub repository contents with v1.1.1 while preserving `.git`.
3. Commit and push.
4. Deploy `alpaca-138-research-web` first.
5. Confirm migration `002_quarterly_tranches.sql` appears in `/health`.
6. Deploy the worker.
7. Run a new v1.1 smoke test.
8. Create a new v1.1 full run.

Existing v1.0 data is not deleted. A v1.0 full run cannot be treated as the v1.1 staged protocol because the new interim looks and stopping rule change the protocol hash. The unique-index migration allows a new full run for the new protocol while preserving the old one.

## Quarterly workflow

The full run begins with 2024 Q1. At completion, the UI provides:

- **Quarter** — standalone Q1 package;
- **Cumulative** — 1 January 2024 through Q1 package.

If the futility gate is not triggered, the worker automatically starts 2024 Q2. The same process continues through 2025 Q4. The browser may be closed throughout.

## Resume

- A worker restart normally requires no action.
- A stale partition is reclaimed after 20 minutes.
- A permanently failed partition changes the run to `failed`.
- Use **Retry and resume** once; completed quarters and partitions remain complete.
- Never delete the Supabase project or clear the tables to recover a run.

## Checking whether it is frozen

The dashboard displays the active partition and heartbeat age.

- Green and under 20 minutes: active.
- Red and over 20 minutes: probably stale; the worker should reclaim it.
- No active partition with queued work: inspect Render worker logs.
- `failed` status: use **Retry and resume** after correcting the error.

SQL detail:

```sql
select stage,partition_key,status,attempts,max_attempts,row_count,cursor,
       heartbeat_at,now()-heartbeat_at heartbeat_age,left(last_error,500) last_error
from work_partitions
where run_id=(select id from research_runs order by created_at desc limit 1)
order by case status when 'running' then 1 when 'failed' then 2 when 'queued' then 3 else 4 end,
         updated_at desc;
```
